# Firmware data reference

`main.py` produces two JSON files in the repo root. Both are keyed by the **firmware file name**, so join them on that
key. `docs/examples/` has real output for 32 firmwares across 11 vendors, generated by the actual pipeline. It includes
one example of each case a site needs to handle:

| Case | Example |
|---|---|
| Listed by two vendors | `General_NVR5XXX-4KS2_MultiLang_V4.002.0000000.8.R.241030.bin` (EmpireTech and Inaxsys) |
| Identical files under several names | `LH0604_20190925_00058.bin` (`aliases`), `LH0604P…` and `LH0704…` (`duplicate_of`) |
| A vendor's previous firmware (`latest: false`) | `General_SD6A8XXX-HN-L_MCU…`, `General_SD50XXX-HN_MCU…` |
| Truncated file, IDs recovered from its intact part | `DH_IPC-HX5XXX-Volt…` (`integrity.status: truncated`, result `truncated: true`); also archived, with a dead vendor link |
| `extract_failed` | `General_ASR1100B_APP…` |
| `not_dahua` | the GSS Red\|LINE `.dav` files (Hikvision) and the Lorex `LH0604…` group (`platform: unknown`) |
| `url_status` `ok`, `dead`, `error`, `unchecked` | most listings; `DH_IPC-HX5XXX-Volt…`; `ATC-1202W.zip`; the MEGA, Drive and SharePoint listings |
| Not analysed yet ("analysis pending") | `ATC-1202W.zip` (in `cameras.json` only; it was never downloaded) |


## `cameras.json`: where each firmware came from

```json
"DH_IPC-HX1X3X-Kant_EngSpnRus_PN_V2.860.0000000.40.R.260515.zip": {
    "camera_name": ["IPC-HFW1439S1-A-IL", "IPC-HFW1230S1-A-S6", "IPC-HFW1230TC-A"],
    "changelog": "https://materialfile.dahuasecurity.com/uploads/cpq/84464/firmware/DH_Kant_Platform_Release_Notes.pdf",
    "firmware_size": 15532655,
    "firmware_version": "V2.860.0000000.40.R",
    "md5": "cb7aae9bad465cc2096f946357a88316",
    "notes": [],
    "release_date": "2026-05-29",
    "sha256": "4ec9c1a0fc936372791040e9abd7463540c703a4bf6295f73ef8a86138e35092",
    "url": "https://materialfile.dahuasecurity.com/uploads/cpq/84464/firmware/DH_IPC-HX1X3X-Kant_EngSpnRus_PN_V2.860.0000000.40.R.260515.zip",
    "vendors": ["Dahua"]
}
```

| Field | Always present | Description |
|---|---|---|
| `camera_name` | yes | Model names **as the vendors list them**: OEM SKUs (Amcrest `IP2M-841`, EmpireTech `IPC-T54IR-ZE`, Inaxsys `INS324K`) or Dahua models. Combined from every vendor that lists this file. Names that are really firmware file names are dropped, series names move to `series`, and descriptions vendors put in the model column ("Full Color firmware", "32 Channel Firmware (Older than 2020)") move to `notes`. A model with a bracketed description keeps the model. Can be empty. |
| `series` | optional | Product series or family names vendors listed in place of a model, e.g. `NXL Series`, `IPC-HX3(2)XXX`, `NVR4xxx`. Useful as a grouping, but not single models. |
| `notes` | yes | Free-text vendor notes, e.g. `"Only for IP2M-841 German and Italian"`, `"Product line: Diamond/PTZ"`, `"Compatible models: NR32P4-4C"`. RVI notes are in Russian. Often empty. |
| `url` | yes | Download URL from the most recent listing. May be a plain file, a MEGA link (EmpireTech), a Google Drive download link (ENS), a SharePoint link (Inaxsys) or a redirect API (RVI), so treat it as "where to get it", not as a file name. Links can die; `url` is the last place it was seen. |
| `vendors` | yes* | Vendors that list this file, e.g. `["Dahua", "EmpireTech"]`. Values: `Amcrest`, `Dahua`, `EmpireTech`, `ENS Security`, `GSS`, `Inaxsys`, `Lorex`, `Montavue`, `Optiview`, `Rhino`, `RVI`, `Speco`, `VIP Vision`, plus `ASM` (a Czech distributor's file server). Mirror and archive sources count as the vendor whose files they hold. *Entries no vendor has listed since vendor tracking was added have no `vendors` yet. |
| `downloadable`, `listing_only_reason` | listing-only | `downloadable: false` marks a firmware a vendor lists but that can't be downloaded (e.g. KBVision's SharePoint links need a login), with the reason. There's no file, so it has no hashes, analysis or archive copy. Show it as "known, not downloadable". Both fields go away if another source provides the file. |
| `file_type` | yes | Always `firmware`. **Both JSONs only describe firmware**: PC software, apps, plugins, drivers, OS images and documents that some sources list next to firmware are skipped before download when the name gives them away, and otherwise moved out of `firmware/` (to `firmware-non-firmware/`) with their entries removed once their content shows it. |
| `firmware_size` | once downloaded | Size in bytes of the downloaded file. |
| `platform` | once downloaded | `dahua`, `hikvision` or `unknown`, identified from the file's header (looking inside zips) and Dahua's file naming. **Not every vendor here only sells Dahua**: GSS Red\|LINE is Hikvision, and some Lorex, FLIR and old Amcrest analog DVRs are other platforms (`unknown`). Filter on this before treating a firmware as Dahua-compatible. |
| `firmware_version` | optional | Version without the build date, the way a Dahua device shows it (`V2.860.0000000.40.R`). Left out when the only "version" a vendor gives is the file name itself (GSS, Montavue). |
| `release_date` | optional | `YYYY-MM-DD`: the **earliest** date any listing gives (when the firmware first appeared), otherwise the build date from the version string. Each listing keeps its own `release_date`. |
| `changelog` | optional | URL to release notes (PDF/TXT). |
| `md5`, `sha256` | optional | Checksums published by the vendor (Dahua Download Center only). Downloads are verified against `md5`. |
| `vendor_md5_mismatch` | rarely | `true` when the file's MD5 doesn't match the one the vendor published. Dahua occasionally publishes a wrong checksum; a file is only kept despite that when two separate downloads were byte-identical. The file is still checked by `integrity`. |
| `file_hashes` | once downloaded | `{"md5", "sha256", "size", "mtime"}` of the file actually on disk, for every vendor. `size`/`mtime` are only there so hashes are recomputed when the file changes. |
| `integrity` | once downloaded | `{"status": "ok" \| "truncated" \| "unverified", "reason"}`. Zip-style files (most Dahua firmware) must end with an intact zip directory; a cut-off download doesn't. `unverified` means the format can't be checked this way (e.g. Hikvision `.dav`). `vendor_copy_truncated: true` means the vendor serves the same cut-off file, so there's no complete copy to get. **Show a warning on truncated firmware: it can't be installed.** Truncated files are re-downloaded when a source has a different copy (the cut-off one is kept in `firmware-truncated/`), and aren't uploaded to the archive. |
| `aliases` | when duplicated | Other file names with **byte-for-byte identical** content (same `sha256`). This entry is the main one: give it the page, and redirect the aliases to it. |
| `duplicate_of` | when duplicated | Set on the other copies: the main entry's file name. Merge this entry's listings into the main page, and redirect its URL there. Duplicates share the main entry's `archive_url`/`archive_item` and analysis. |
| `listings` | once listed | **What each vendor page says, kept separately.** One object per vendor page (see below). Use this to say "EmpireTech sells this as IPC-T54IR-ZE" or to offer every vendor's download link. Firmwares that no vendor lists anymore get one inferred from their download host, with a `source` like `dahuawiki.com (found in an earlier scrape)`. |
| `archive_item` | once archived | Internet Archive item page for this firmware, e.g. `https://archive.org/details/cctv-firmware-...`. |
| `archive_url` | once archived | **Permanent direct download** from the Internet Archive. Prefer this over `url`, since vendor links break. For firmwares no vendor hosts any more, it's the only working link. |
| `archive_md5`, `archive_record_hash` | once archived | Bookkeeping for the archive step (the MD5 of what was uploaded, and a hash of the metadata last sent). The site can ignore them. |

The top-level `camera_name`, `notes`, `url`, `firmware_version`, `release_date` and `changelog` combine all vendors
(the `url`, version and date come from whichever listing was processed most recently). `listings` has the per-vendor
detail:

```json
"listings": [
    {
        "vendor": "EmpireTech",
        "source": "EmpireTech",
        "camera_name": ["NVR5208-8P-4KS2E", "NVR5216-16P-4KS2E"],
        "notes": [],
        "url": "https://mega.nz/folder/...",
        "firmware_version": "V4.002.0000000.8.R",
        "release_date": "2024-11-02"
    },
    {
        "vendor": "Inaxsys",
        "source": "Inaxsys STORM",
        "camera_name": ["INS8824KN"],
        "notes": ["STORM NVR"],
        "url": "https://inaxsys.sharepoint.com/...?download=1",
        "firmware_version": "V4.002.0000000.8.R",
        "release_date": "2024-10-30"
    }
]
```

| Listing field | Description |
|---|---|
| `vendor` | Vendor name, same values as `vendors`. |
| `source` | Which page or module of that vendor listed it, e.g. `Dahua Download Center` vs `DahuaFileDirectory` (dahuawiki), or `GSS - Blue\|LINE NVR`. A vendor can have several listings from different sources. |
| `camera_name`, `notes`, `url` | That vendor's own model names, notes and download link. |
| `series` | Series names that vendor listed instead of models (see top-level `series`). |
| `firmware_version`, `release_date`, `changelog` | That vendor's details. When a vendor gives no version (e.g. Amcrest's previous-firmware column), they're taken from the Dahua-style file name. |
| `first_seen`, `last_seen` | `YYYY-MM-DD` of the first and most recent run this page listed the file. A `last_seen` older than the newest run means the vendor has stopped listing it. Use `first_seen` for "newly added firmware" pages and feeds. Tracking started 2026-10-02, so everything older shows that date. |
| `kind` | Always set. `vendor`: the vendor's own download page. `mirror`: a distributor's or support file server that just holds copies (ASM's `ftp.asm.cz`, `files.dahuatech.support`). `archive`: a Wayback Machine capture of a file the vendor no longer serves. Say "available from" for vendors, "mirrored by" for mirrors, and "recovered from the Wayback Machine" for archives. |
| `latest` | `true` if this page lists it as its **current** firmware (rather than a previous one) in its most recent listing. Only on `kind: vendor` listings; mirrors and archives don't say which firmware is current. |
| `url_history` | Every URL this page has offered the file at, oldest first, each with `first_seen` and `last_seen`. Only present when there has been more than one: vendors move files between folders (Rhino moved `/dvr/` into `/dvr/Dahua/...`) and list one file under several products (Amcrest's per-camera S3 folders). `url` is the most recent. Old addresses are worth showing as "previously at" links and for finding Wayback copies. |
| `original_url`, `archived_at` | Only on `kind: archive`: the URL the file was originally published at, and the date the Wayback Machine captured it. `url` is the Wayback download link. |
| `last_seen_latest` | Bookkeeping for `latest`: the last run it was listed as current. |
| `url_status`, `url_checked_at` | From `python main.py check-links`: `ok`, `dead` (404/410, or S3's 403 for a missing file), `error`, or `unchecked` (MEGA, Google Drive and SharePoint links aren't checked). Absent until the first check. When it's `dead`, point people to `archive_url`. |

`last_seen` is per source: a run limited with `--only`/`--skip` only refreshes the listings of the sources it ran, so the others keep their earlier dates.

Inferred listings (`source` ending in `(found in an earlier scrape)`) come from data older than listing tracking, so
they have no `first_seen`/`last_seen`.

If two different files have the same name, the second one is stored as `<name>-<8 hex chars>.<ext>` instead of being
treated as the file already on disk. That's decided by comparing sizes, so it only works where the size is known
up front (most hosts; not some Google Drive files).

## Internet Archive

Every downloaded firmware is uploaded to its own Internet Archive item (`python main.py archive` runs just that
step). All items are tagged `amcrest-compatible-finder`, so the whole archive is listed at
https://archive.org/search?query=subject%3A%22amcrest-compatible-finder%22. Each item's description repeats the
vendors, model names, hardware IDs, version, checksums and original URL, and an
`<file>.provenance.json` in the item has the same data machine-readably.

Identical copies (`duplicate_of`) are not uploaded again. Their main entry's item lists every alias file name and
where each was published, and the duplicates' `archive_url`/`archive_item` point at that item.

## `firmware_compatible.json`: what hardware each firmware supports

One object per firmware file, describing what unpacking it found:

```json
"DH_IPC-HX1X3X-Kant_EngSpnRus_PN_V2.860.0000000.40.R.260515.zip": {
    "hardware_ids": ["IPC-B1E29-A-IL-S2", "IPC-HFW1230B-A-IL", "IPC-HFW1230S1-A-S6", "..."],
    "hardware": {"models": ["IPC-B1E29-A-IL-S2", "..."], "boards": [], "hwids": [], "ignored": []},
    "status": "ok",
    "extractor_version": 2,
    "processed_at": "2026-10-02T17:31:39+00:00"
},
"K74_V3.4.98_180104-1.dav": {
    "hardware_ids": [],
    "status": "not_dahua",
    "platform": "hikvision",
    "extractor_version": 2,
    "processed_at": "2026-10-02T17:31:39+00:00"
}
```

| Field | Description |
|---|---|
| `hardware_ids` | Sorted **hardware IDs read from inside the firmware**: the board/model IDs its installer accepts (from `check.img` hwids, the `hwid` file, `Install`/`Install.lua`, or the u-boot image name; see `hardware_sources` for which). This is what the firmware will install on, and it's usually much longer than the vendor's `camera_name` list. Empty unless `status` is `ok`. |
| `hardware` | The same IDs, **already cleaned up and sorted**: `models` (single devices, e.g. `IPC-HFW1230S1-A-S6`), `boards` (families with placeholders, e.g. `HCVR5x04-S2`, `NVR4X-4KS2/L`, `IPC-HX3XXX`), `hwids` (raw 16-hex-digit IDs), and `ignored` (vendor tokens like `DAHUA`, RVI's `Group`, and leftover file names). `General_X` is folded into `X`. Use this instead of `hardware_ids` for search and model pages. |
| `status` | `ok`: hardware IDs found. `no_ids`: unpacked fine, but none of the known ID sources were in it (often MCU, access control or thermal firmware). `extract_failed`: couldn't be unpacked (see `error`). `not_dahua`: not analysed because `platform` isn't Dahua. `duplicate`: an identical copy of `duplicate_of`, whose result it repeats. |
| `extractor_version` | Version of the analysis that produced this. `1` means the old analysis, before statuses existed. Results without IDs are re-analysed when the version goes up; version 5 also re-analyses older `ok` results to add `hardware_sources` and `packages`. |
| `processed_at` | When it was analysed (UTC, ISO 8601). Absent on version 1 results. |
| `platform` | Only on `not_dahua`: the detected platform (`hikvision` or `unknown`). |
| `truncated` | `true` when the file is truncated: the IDs come from the complete entries at its start (the installer metadata usually survives), so they're likely right, but the firmware itself is unusable. |
| `error`, `attempts` | Only on `extract_failed`: what went wrong, and how many times it was tried with this extractor version (retried up to 3 times). |

A firmware that's in `cameras.json` but **missing here hasn't been analysed yet**, so show it as "analysis pending".

### Hardware ID sources, packages and partitions (extractor version 5+)

Version 5 results also say **where each ID came from** and **what the firmware says about itself**. Older results
lack these fields; they're re-analysed to fill them in. `hardware_ids` / `hardware` stay the union of every source.

```json
"hardware_sources": [
    {"source": "install", "member": "Install", "firmware": null,
     "ids": ["IPC-HX3XXX"], "raw": [["IPC-HX3XXX", "1.00"]], "vendor": "General", "counted": false},
    {"source": "check_img", "member": "check.img", "firmware": null,
     "ids": ["IPC-HFW2541SP-S", "..."],
     "raw": ["IPC-HFW2541SP-S:01:02:04:C8:62:00:01:10:01:00:04:4B0:00:00:00:00:00:01:00:00:100", "..."],
     "counted": true}
],
"package_format": "dh",
"packages": [{
    "firmware": null,
    "package_format": "dh",
    "architecture": "arm",
    "soc": {"name": "S3L", "vendor": "Ambarella",
            "evidence": [{"source": "bootloader", "member": "dhboot-min.bin.img", "value": "ambarella,s3l"}]},
    "partition_source": "partition_table",
    "partition_table": "partitionV2.txt",
    "partitions": [
        {"name": "Kernel", "image": "kernel.img", "start": "0xf0000", "end": "0x270000", "size": 1572864,
         "image_size": 1487004, "image_name": "kernel", "image_type": "firmware", "filesystem": null,
         "compression": "none", "built": "2017-05-23", "upgraded": true, "backup_start": "0x18d0000"},
        {"name": "config", "image": null, "start": "0x1aa0000", "end": "0x1b10000", "size": 458752,
         "image_size": null, "image_name": null, "image_type": null, "filesystem": "jffs2", "compression": null,
         "built": null, "upgraded": false, "read_only": false}
    ],
    "flash_size": 33554432,
    "build_dates": {"earliest": "2017-05-23", "latest": "2017-05-23"},
    "kernel_version": "3.10.73",
    "bootloader_version": "U-Boot 2010.06-svn4423",
    "oem_vendor": "General",
    "security": {"security_baseline": "V2.4", "upgrade_security_version": null, "signed": true, "encrypted": false,
                 "checks": {"SecurityBaselineVersion": "V2.4,"}},
    "locale": {"default_language": "English", "video_standard": "PAL", "supported_languages": ["English", "..."]}
}]
```

| Field | Description |
|---|---|
| `hardware_sources[]` | One entry per place that lists hardware. `source`: `hwid` (the `hwid` file), `check_img` (`check.img`'s hwid list), `install` (`Install`'s `Devices`), `install_lua` (`Install.lua`'s `board.name`/`vendor.Name` checks) or `uboot` (the u-boot image's board name, only used when nothing else lists hardware). `member`: path inside its container. `firmware`: the inner firmware's file name in a bundle, else `null`. `raw`: the full hwid entries (the part after the first `:` encodes hardware revision details) or `Install`'s `[id, version]` pairs. `vendor`: `Install`'s `Vendor`. The hwid and `check.img` lists are what the device itself checks before installing, so they're the most reliable; `Install` lists board families; `install_lua` can include generic names like `DAHUA`. `counted`: whether these IDs are in `hardware_ids`. Every source is listed, but within one folder of one firmware only the most specific one counts (hwid/`check.img`, then `install`, then `install_lua`, then `uboot`), so a board family like `IPC-HX3XXX` doesn't make a firmware look compatible with every camera in that family. |
| `package_format` | The file's container: `zip`, `dh` (Dahua's zip variant with `DH` signatures), `dhsp` (PTZ variant), `bundle` (a zip or `.bin` holding two or more firmwares) or `other` (not zip-style; read by binwalk). |
| `packages[]` | One per firmware image set: the file itself, or each firmware nested in a bundle (`firmware` names it; a plain wrapper zip around one `.bin` gives one package named after the `.bin`). |
| `packages[].architecture` | CPU architecture from the image headers (`arm`, `arm64`, `mips`...). |
| `packages[].soc` | The SoC, or `null`. `name` (e.g. `Hi3516CV500`, `SS528V100`, `Infinity6C`, `NT98336`, `RK3588`, `S3L`) and `vendor` (HiSilicon, SigmaStar, Novatek, Rockchip, Fullhan, Goke, Ingenic, Ambarella, Molchip, Axera); either can be `null` when only the other is certain (e.g. a device tree that only says `novatek,na51089`). `evidence` lists what it's based on, strongest first: `device_tree` (the root `compatible`/`model`), `bootloader` (chip names in the boot loader), `image_name` (recorder images named after the chip, like `3535romfs` or `5x16FW98336Tboot`), `kernel`. Conflicting chips leave `name` null and list them in `candidates` (e.g. a boot loader built for `Hi3520DV300`, `Hi3521A` and `Hi3531A`). |
| `packages[].partitions[]` | The flash layout, sorted by `start`. `start`/`end` are hex strings exactly as the firmware gives them, `size` and `image_size` are bytes. Partitions this firmware writes have `image` (the member), `image_name`, `image_type` and `compression` (from its uImage header; Dahua doesn't use the type codes consistently, so don't rely on them), `filesystem` (`squashfs`, `cramfs`, `jffs2`, `ubi`... from the image's content, else the table or member name), `built` (header date) and `upgraded: true`. Partitions in the table that it leaves alone (config, logs, backups) have `upgraded: false` and null image fields. Tables from `partitionV2.txt` add `read_only` and `backup_start` (where the backup copy lives) when set. **Addresses:** recorder image headers and some recorder `Install.lua` tables use memory-mapped addresses (`0xa0000000` = start of flash); IPC tables and `Install.lua` tables starting at `0x0` are flash offsets. |
| `packages[].partition_source` | Where the layout comes from: `install_lua` (recorders' `flashPartions` table: every partition), `partition_table` (IPCs' `partition-x.cramfs.img`, whose `partitionV2.txt`/`partition.txt` lists every partition; `partition_table` names the file), `image_headers` (only the partitions this firmware writes, from each image's header, named by `Install`'s burn commands), or `null`. `partition_table_variants` lists board-specific tables when there's no main one (none is used then). `unmapped_images` lists images that didn't match a table partition. |
| `packages[].flash_size` | Total flash in bytes: the end of a complete table (`install_lua` or `partition_table`), else `null`. `flash_size_declared` / `flash_type` are `check.img`'s `FlashSize` / `FlashType` when present (e.g. `16M`, `SPI`). |
| `packages[].build_dates` | `{earliest, latest}` of the image header dates, or `null`. |
| `packages[].kernel_version` | Linux kernel version from the kernel image's banner (e.g. `4.9.37`), or `null` (no separate kernel, or encrypted). |
| `packages[].bootloader_version` | e.g. `U-Boot 2019.04-svn13580`, from the boot loader images, or `null`. |
| `packages[].oem_vendor` | `Install`'s `Vendor`: which OEM build this is (`General`, `Amcrest`, `Dahua`...). `oem_vendor_checks` lists the vendor names `Install.lua` accepts. |
| `packages[].security` | `signed`: a `sign.img` signature is included. `encrypted`: `true` when every filesystem/kernel image is unrecognisable high-entropy data, `false` when they're all recognisable, `null` when mixed or unknown. `security_baseline`: the security baseline version (`Install.lua`'s check, else `check.img`'s `SecurityBaselineVersion`), e.g. `V2.4`. `upgrade_security_version`: `Install.lua`'s `UpgradeSecurityVersion`. `checks`: raw security/rollback settings from `check.img` and `Install` (e.g. `HardwareSecurityVersionMajor`, a minimum-hardware-security check); `script_checks`: raw rollback / minimum-version lines from `Install.lua`. A firmware with a higher baseline than the device may not be downgradable. |
| `packages[].locale` | From `check.img`: `default_language`, `video_standard` (`PAL`/`NTSC`) and `supported_languages`, or `null`. |
| `packages[].software_version`, `market_area` | `Install`'s `Version.SoftwareVersion` and `MarketArea` when present. |

- **Hardware IDs are the cross-vendor link.** Two firmwares from different vendors that share hardware IDs run on
  the same hardware. For example, an Amcrest SKU can be matched to the Dahua or EmpireTech firmware for the same
  board.
- Use `hardware.models` and `hardware.boards` for search; `hardware.hwids` only identify a board, and
  `hardware.ignored` aren't models at all.

## Suggested site model

1. **Firmware pages**: one per key that has no `duplicate_of`, combining both files and the listings of its
   `aliases`. Redirect alias keys to the main page. Show each vendor's listing (their model names, notes and
   link), the version, release date, changelog, size and checksums, the hardware ID list, and the Internet Archive
   download (`archive_url`) as the primary link.
2. **Hardware pages**: invert `hardware.models` and `hardware.boards` in `firmware_compatible.json` to get `model -> [firmware files]`, sorted by
   `release_date` (newest first) so the latest compatible firmware from any vendor is at the top.
3. **Model search**: index both `camera_name` (vendor SKUs) and the hardware IDs, so searching for an OEM SKU leads
   to its firmware and then to every other firmware for the same hardware.
4. **New firmware**: sort listings by `first_seen` for a "newly added" page or feed, and use `latest` to badge each
   vendor's current firmware.
